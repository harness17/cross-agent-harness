# Cross-Agent Harness

Codex と Claude Code が同じリポジトリで安全に作業するための共通ルール。

## 基本方針

- 作業開始時に `CLAUDE_CODE_HANDOFF.md` の最新セクションを読む。
- プロジェクト固有の判断は `.claude/rules/project-collaboration-profile.md` を優先する。
- 既存の未コミット変更を自分の変更として扱わない。重なる場合は止めて確認する。
- 実装・レビュー・検証の担当境界を handoff に明記する。
- merge / publish はユーザーの明示指示なしに進めない。

## 作業開始（実装・レビュー担当）

1. `git status --short --branch` で worktree を確認する。
2. `CLAUDE_CODE_HANDOFF.md` の最新セクションから目的、触ってよい範囲、検証方法を読む。
3. 仕様が曖昧な場合は、推測で広げず完成条件を確認する。
4. handoff に書かれたパス・契約・削除対象に不足があれば、開始前に依頼者へ確認する。実体ファイル名と齟齬がある場合（過去事例: `db/index.js` → 実体 `schema.js`、`channelsRepository` → 実体 `channelRepository`）は依頼者の意図を確認してから進める。

## 依頼起票（設計担当）

1. handoff に書くファイルパスは実体で確認する。`ls` / `grep` で存在を確認してから記述する。
2. 複数層に跨る契約（Electron の IPC、API ↔ クライアント、サービス境界など）を含む依頼は対称性を保って記述する。発火側・受信側・公開層・呼び出し側のいずれかが欠けると後工程で迷う。Electron IPC の例:
   - main handler / preload exposure / renderer 呼び出し / event 発火・購読ペア の 4 点を完成条件に列挙する。request/response 型で event ペアが該当しない場合は `N/A: 理由` を明記する。
3. コンポーネント・ファイル置き換え時は「削除すべきファイル」を handoff に明記する（テンプレの top-level 項目）。新規作成と旧ファイル削除を 1 つの依頼内で扱う。
4. UX 大規模変更は事前にモック・ASCII 図・参考スクショなど低コスト案を依頼者と共有してから依頼起票する。実装後の手戻りを防ぐ。

## 作業中

- 触るファイルを最小化する。
- 相手エージェントの変更を巻き戻さない。
- 設計判断、検証結果、未解決リスクは handoff に残す。
- セキュリティ、認可、個人情報、外部 API quota、公開判断はプロジェクト profile の重大指摘に従う。公開に関わる作業は下の「公開前の機密チェック」も行う。
- UX 大規模変更（タブ統合・新規ハブコンポーネント等）は実装完了直後にスクリーンショットや短い動画で依頼者に共有し、想定とのズレを早期に検出する。事前のモック共有（依頼起票セクション参照）と合わせて二段で確認する。

## 公開前の機密チェック

次のタイミングで、外に出る中身に機密が混ざっていないかを確認する。

- リポジトリを新しく公開するとき、private から public に切り替えるとき
- 記事・ポートフォリオ・README など、外部から読める文書を公開・更新するとき
- 既存コードやテンプレートを取り込んだ変更を merge / publish するとき

確認は今のファイルだけでなく、git 履歴（過去のコミットで消した内容）も対象にする。

### 観点

1. **接続情報・認証情報**: 接続文字列、パスワード、API キー、トークン、実在の IP アドレスやホスト名（`localhost` やダミー値以外）。環境別の設定ファイル（`Web.*.config`、`App.*.config`、`appsettings.*.json`、`.env`、発行プロファイル）は中身を開いて確認する。
2. **社名・顧客名・案件名**: 前職・取引先・顧客の名前、案件コード、社内システム名。リソースファイル（`.resx` など）、画面の文言、システム名の定数に残りやすい。
3. **社内の URL・パス・機器名**: 社内 Wiki やチケット管理の URL、ドライブ名付きの社内フォルダパス、社内 PC やサーバーのホスト名。ビルドスクリプトや設定ファイルに残りやすい。
4. **業務固有の名残り**: 元の案件の業務用語やメッセージがまとまって残っていないか。一語ずつは汎用でも、まとまると元の案件が特定できる。
5. **メタ情報**: `AssemblyInfo` などの会社名・著作権表記、テンプレートの既定タイトル、コミットの作者情報。
6. **由来**: 業務で書いたコードを元にしたものは、原則として公開しない。公開するなら、元のコードを使わず書き直したことを確認する。

### 見つかったとき

- その時点で merge / publish のブロッカーにし、ユーザーに報告する。報告にパスワードなどの値そのものは書かない。
- すでに公開済みなら、まず非公開にする。ファイルを消すコミットだけでは履歴に残るので、リポジトリの作り直しなど履歴ごと消す方法をユーザーと決める。
- そのリポジトリや記事を参照しているリンク・記事・書類も洗い出して整理する。
- 接続情報が公開されていた場合は、持ち主にパスワード変更などを伝えるかどうかをユーザーに判断してもらう。

## 完了条件

- 完成条件を満たす。
- profile の verify コマンドを実行し、結果を handoff に記録する。
- 実行できない検証は理由と代替確認を記録する。
- 反対側レビューが必要な場合は、レビュー観点を明示して依頼できる状態にする。
